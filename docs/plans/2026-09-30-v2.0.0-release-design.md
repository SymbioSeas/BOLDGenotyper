# BOLDGenotyper v2.0.0 release — design

Date: 2026-09-30
Status: Phases 0–5 reviewed and approved; Phase 6 done, awaiting review
Branch: `release/v2.0.0` (from `main` at `8a19d4a`)

## Problem

A review of a full Carcharhiniformes run (BOLD portal download of 30 Sep 2026,
9,785 rows) against v1.0.0 found values that are wrong, outputs that cannot be
reproduced from what the run records, and default interpretations that do not
generalize across taxa:

- **P0 (12 items): correctness and reproducibility.** Examples: the parameters
  file omits the swept parameter; every unassigned record is labeled
  `no_sequence`; the assignment summary reports 100% assigned; the tree silently
  drops haplotypes; haplotype IDs embed a member count that disagrees with every
  other file.
- **Q1–Q10: `boldgenotyper-query`.** Gap characters in the input are counted as
  sequence, indels are invisible to identity, there is no coverage metric, the
  tie margin is a percentage whose meaning depends on query length, and species
  support comes from majority labels rather than member labels.
- **P1 (10 items): default interpretations** (thresholds, "contamination",
  "misidentification confidence", "emergence", representativeness labels).
- **P2: redundancy.** A run writes about 248 files (332 MB), including a 95 MB
  HTML report and several byte-identical duplicates.
- **P3: polish.**

The changes alter haplotype IDs, the output layout and query flags, so under
the project's semantic-versioning commitment this is **2.0.0**.

## Goals

- Every number a run reports is correct, defined, and traceable to a recorded
  parameter.
- A run can be reproduced from `run_provenance.json` alone.
- Haplotypes have a stable cross-run key (`seq_md5`) and IDs that carry no counts.
- `boldgenotyper-query` reports what a query can and cannot resolve, in numbers.
- The default output is small (about 15 files) and documented file-by-file.
- v1 users can migrate: removed CLI flags stay as deprecated aliases, and a
  migration table maps every v1 file and column to its v2 equivalent.

## Non-goals

- Changing how haplotypes are discovered. For identical input and
  `--singleton-distance`, v2.0.0 must produce **the same set of haplotype
  sequences** as v1.0.0 (checked by `seq_md5` in Phase 7).
- Re-running the published analyses (sweeps, full runs, benchmarks). Those follow
  the tagged release.
- GenBank `.gb` input (`origin/dev_gb_input` stays out of 2.0.0).

## Phase 0 findings that refine the review

Reading the code against the v1 run changed four diagnoses. The fixes below
follow the code, not the original guess.

1. **P0-12 is not a double load within one run.** `utils.setup_logging` opens
   the log with `mode='a'`. The v1 log contains an interrupted first invocation
   (it stops while loading the GOaS shapefile, 8 s in) followed by a complete
   second invocation, which is why lines 14–32 repeat at 46–64. Only one
   "Pipeline completed" line exists, and nothing in `run_pipeline` re-reads the
   TSV (`dereplication.identify_haplotypes` uses `tsv_path` only for file
   names; the one `mp.Pool` is in the unused legacy `metadata.assign_genotypes`).
   Fix: a fresh log per run with a run header, plus a guard test that the input
   is parsed once.
2. **P0-4: coordinates are parsed; the quality flags are wrong.** Every `coord`
   value in the current portal export has the form `[lat, lon]` (integers or
   decimals, any sign), which the existing parser handles. Of 3,481 raw records
   with coordinates, 1,457 carry `coord_source = "Coordinates from country
   centroid"` (plus 1 province centroid). Excluding those is correct. The bugs:
   - `metadata.mark_coordinate_quality` tests `latitude`/`longitude` columns
     that portal TSVs do not have, so records with **no** coordinates are marked
     `is_geographic_quality = True`, and zero or out-of-range coordinates are
     never flagged.
   - `lat`/`lon` are written back only for the geo-quality subset, so
     centroid-coordinate records lose their coordinates in the annotated table.
   - Missing regions are encoded both as `'Unknown'` and as NaN.

   Consequence: in v2, `lat`/`lon` will be present for essentially every record
   with a `coord`, but regions (basins) are assigned only to records whose
   coordinates are parseable, non-zero, in range and not a centroid, and that
   fall inside a region polygon. Region counts will rise only by what the
   quality-flag fix recovers, not to "all records with coordinates."
3. **P0-1: the coverage "conflict" is two different thresholds, both applied.**
   `core_region.core_min_coverage = 0.8` is a *column* rule (a position joins the
   core if at least 80% of sequences cover it). The "95%" in the log is a
   separate, hard-coded *per-sequence* rule in `utils.extract_core_region`: a
   record needs at least 95% of the 95th-percentile ungapped core length. Only
   the first was recorded.
4. **P0-7 and P0-8 are coupled.** `phylogenetics._extract_cluster_size` parses
   the `_n` suffix of the haplotype ID to apply the tree membership filter. With
   count-free IDs it must read `n_members=` from the FASTA header instead.

Also relevant to P0-8: after the zero-divergence merge,
`dereplication.merge_zero_divergence_haplotypes` keeps the representative's
original ID, and `haplotype_mapping['n_members']`/`is_singleton` are never
recomputed. That is the source of `h1_n354` having 422 members.

## Design

### Cross-cutting: internal keys and display IDs

Inside `dereplication`, a haplotype is keyed by `seq_md5` from the moment it is
discovered. Nothing parses member counts out of an ID string: filtering,
flagging and merging read counts from the mapping table. Display IDs (`H0001`)
are assigned **once**, after error-singleton correction, from final
`n_members` (`n_exact + n_corrected`) descending, then `seq_md5` ascending. With
`--no-assign-corrected`, `n_corrected` is 0 and numbering follows `n_exact`.

A new focused module, `boldgenotyper/haplotype_ids.py`, owns `seq_md5()`,
`assign_display_ids()`, `format_fasta_header()` and `parse_fasta_header()`, so
the pipeline, tree code, exports and query tool share one definition.

FASTA header: `>H0001 seq_md5=<32 hex> n_members=<int>`. Biopython's `.id` is
`H0001`, so downstream code that reads IDs keeps working.

### Cross-cutting: step warnings and run status

A new module, `boldgenotyper/provenance.py`, holds a `StepWarnings` collector.
Every `except` block in `run_pipeline` that skips a step or figure calls
`warnings.record(step, message)` (several currently log such failures at
`debug`; they are raised to `warning`). Data-quality notices (duplicate
processids, coordinates outside all regions) stay in the log and go into
provenance as `data_notes`, not into the warnings summary, so a clean run has an
empty summary.

The end of the log becomes:

```
WARNINGS (2):
  - [10.1 distribution map] At least one value in the dash list must be positive
  - [8.3 MSA visualization] pymsaviz not installed
Pipeline completed with 2 warnings for Carcharhiniformes
```

or, with none, `Pipeline completed successfully for <organism>` as the last line.

### P0-1 Provenance

`run_provenance.json` is written at the start of the run (status `running`) and
rewritten at the end, built from `dataclasses.asdict(cfg)` (every field; paths as
strings) plus:

- `boldgenotyper_version`; `git_commit` and `git_dirty` when the package is
  imported from a git checkout (`git rev-parse HEAD` in the package directory;
  omitted otherwise)
- `argv` (list) and `command_line` (`shlex.join`)
- `input`: path, md5, data-row count, unique processids, `download_date` (new
  optional `--download-date YYYY-MM-DD`, validated)
- `tools`: MAFFT, FastTree and trimAl versions (from their version output)
- `applied`: values computed during the run, including
  `core_region_length_bp`, `core_reference_length_bp` (95th percentile),
  `min_sequence_length_bp` (the per-sequence cutoff actually applied),
  `tree_min_members`, `tree_min_length_bp`, `n_tree_tips`, `n_tree_excluded`
- `seeds`: the FastTree seed, now passed explicitly (`-seed 314159`, FastTree's
  own default, so trees do not change)
- `not_applied`: config sections the run did not use, with a reason. The
  `genotype_assignment` section (`min_identity`, `tie_margin`, `tie_threshold`)
  is not used by ESV direct mapping, so it is listed here, not as parameters
- `started_at`, `finished_at`, `status` (`completed`, `completed_with_warnings`,
  `failed`), `warnings`, `data_notes`

The per-sequence core cutoff becomes one named parameter,
`core_region.min_sequence_coverage` (default 0.95, unchanged), passed into
`extract_core_region`; the column rule keeps its name `core_min_coverage`. Both
appear in provenance with a one-line definition in the output README.

The three main-pipeline flags that feed `genotype_assignment`
(`--similarity-threshold`, `--tie-margin`, `--tie-threshold`) have no effect in
the ESV workflow. They become deprecated no-ops that print a warning.

`*_pipeline_parameters.json` is replaced by `run_provenance.json` (Phase 4 moves
it to the new layout; the HTML report reads the new file).

### P0-2 Assignment statuses

One status per unique input record, computed by a pure function in a new module
`boldgenotyper/record_status.py`:

| Status | Meaning |
|---|---|
| `assigned` | Core sequence identical to a retained haplotype |
| `assigned_corrected` | Error-filtered singleton assigned to its nearest retained haplotype |
| `excluded_error_singleton` | Error-filtered singleton equidistant from 2+ retained haplotypes, with no retained haplotype within `--singleton-distance`, or correction disabled |
| `excluded_core_coverage` | Ungapped core length below the per-sequence cutoff (or empty core) |
| `failed_qc` | Failed pre-alignment QC (length, N fraction, ORF); the reason is kept |
| `no_sequence` | No sequence in the input |

Columns added where relevant: `nearest_haplotype`, `distance_to_nearest`,
`status_note` (true for each status; e.g. "Singleton within 0.015 of H0003;
assigned to nearest retained haplotype", "Equidistant (0.0034) from H0012,
H0047"). `extract_core_region` returns the headers it removed so the pipeline
knows who was excluded for coverage rather than inferring it from absence.

Correction: `filter_error_singletons` returns the removed singletons' aligned
core sequences and member processids. After the zero-divergence merge, each is
compared with every retained haplotype using the existing p-distance; the
minimum wins; exact ties (distances equal after rounding to 12 decimals) leave
the record unassigned. The haplotype set is untouched.

Error singletons are identified against all haplotypes, including other
singletons removed in the same pass, so the nearest *retained* haplotype can be
farther than `--singleton-distance` (two near-identical singletons filter each
other out). Records are therefore corrected only when the nearest retained
haplotype is within `--singleton-distance`; farther records stay
`excluded_error_singleton` with a note giving the nearest haplotype and the
distance. Discovery records the reason for each error-singleton record
(`corrected`, `tied`, `beyond_threshold`, `correction_disabled`). On a
2,500-record Carcharhiniformes subsample (threshold 0.015) this gives 319
corrected (all within 0.014), 55 beyond the threshold and 19 tied.

Haplotype tables report `n_exact`, `n_corrected` and `n_members`. Species
composition pools the labels of exact and corrected members.

### P0-3 Assignment summary

Computed from the in-memory status table, not re-derived from CSVs. One row,
explicit denominators:

`n_input` (data rows), `n_unique` (after duplicate removal), `n_no_sequence`,
`n_failed_qc`, `n_qc_pass`, `n_excluded_core`, `n_core_ok`, `n_assigned`,
`n_assigned_corrected`, `n_excluded_error` (with its parts `n_excluded_error_tied`
and `n_excluded_error_far`), `n_haplotypes`, `pct_assigned` = (`n_assigned` + `n_assigned_corrected`) /
`n_qc_pass` × 100, `pct_assigned_exact` = `n_assigned` / `n_qc_pass` × 100, plus
the four P0-9 species counts. Every column in the header has a value.

### P0-4 Coordinates

- `metadata.parse_coord_column(df)` (new) parses `coord` into `lat`/`lon` for
  **every** record: `[lat, lon]` with integer or decimal values of any sign
  (the only format in current portal exports), plus the bracketless
  `lat, lon` form from older exports. Existing `lat`/`lon` columns are used when
  present (legacy exports).
- `mark_coordinate_quality` checks `lat`/`lon` and adds one explanatory column,
  `coord_status` ∈ {`ok`, `missing`, `unparseable`, `centroid`, `zero`,
  `out_of_range`}. `is_geographic_quality` = `coord_status == "ok"` (parseable,
  non-zero, in range, not a centroid). Centroid = `coord_source` contains
  "centroid" (country or province).
- Region assignment runs on `is_geographic_quality` records only; `lat`/`lon`
  stay populated for all parsed records.
- One missing-value code: NaN in memory, empty in CSV. `'Unknown'` is no longer
  written as a region. The 80 `'Unknown'` comparisons across the package become
  `notna()` checks (they are listed module by module in the plan).
- Exports log and document how many samples they drop for a missing region.
- **Centroid exclusion is documented** wherever regions are reported: a log line
  in Phase 1.3 ("N records have country- or province-centroid coordinates; they
  keep lat/lon but are not assigned a region or mapped"), the `coord_status`
  definition in the run README (Phase 4), and the user docs and migration guide
  (Phase 5).
- Regression test: a fixture of at most 50 rows from the 30 Sep 2026 portal
  download, covering every `coord` shape present (both signs, integers and
  decimals), country and province centroids, empty `coord`, and a few
  `coord_source` values, with the source and date noted in the test.

### P0-5 Country counts

Country is read from `country/ocean` (portal), falling back to `country`
(legacy). One helper, `geographic_enhancement._country_column(df)`, is used by
both places that count countries.

### P0-6 Distribution map

`visualization.plot_distribution_map` draws gridlines with `linewidth=0,
linestyle='--'`. Matplotlib scales dash patterns by line width, so the pattern
becomes all zeros ("At least one value in the dash list must be positive"). The
width-0 lines are there to show coordinate labels without grid lines, so the fix
keeps that look: a solid style at width 0 (no dash pattern to scale), in a small
helper `_add_map_gridlines(ax)` that a test can draw and save without map data.
Figure failures go to the `StepWarnings` summary.

### P0-7 Tree membership

`--tree-min-members` (default 1) sets `phylogenetic.min_cluster_size`. The
pipeline selects tips itself with a new pure function,
`phylogenetics.select_tree_haplotypes(records, min_members, min_length,
suspect)`, which returns the kept records and `(haplotype_id, reason)` pairs for
the rest. Reasons: `n_members < K`, `length < L bp`, and `suspect: <reasons>`
(the decision is "every non-suspect haplotype", so suspect haplotypes, which
v1 kept, are now excluded and listed). The kept records go to `build_phylogeny`
with its own filters set to pass everything, so its signature does not change.
`_extract_cluster_size` gains `n_members=` as its first pattern for other
callers. The pipeline writes `phylogeny/excluded_tips.txt`
(`haplotype_id<TAB>reason`), logs the count, and records the filter and counts
in provenance.

### P0-8 Haplotype IDs

As in "internal keys and display IDs." Every `_n` parser is updated:
`dereplication.py` (ID creation; singleton counts via `endswith("_n1")` and
`'_n1' in id`; `int(re.search(r'_n(\d+)'))` in the filter, flagger and merger),
`phylogenetics.py` (`_extract_cluster_size`; tip normalization at ~855 and
~1025), `plot_regeneration.py` (~934–944, ~1022), `utils.py` (~814),
`divergence_analysis.py` (README text ~777), `popgen_export.py` (README text
~656), `parameter_sweep.py` (~839), `haplotype_assignment.py` (docstring ~638),
and `cli.py` (labels ~832; the `--phylo-outgroup-label` example ~1955). A final
`grep` for `_n` confirms nothing is left.

### P0-9 Species counts

Four distinctly named counts, each defined in the output README:

| Name | Definition |
|---|---|
| `n_species_labels_input` | Unique non-empty `species` labels among unique input records |
| `n_species_labels_species_level` | Of those, labels naming a species (excludes genus-only, `sp.`, `cf.`, `aff.`, `nr.`) |
| `n_species_haplotype_assigned` | Unique species-level `assigned_sp` across haplotypes |
| `n_species_confident` | Unique species among haplotypes with `majority_fraction` ≥ `taxonomy.majority_species_threshold` (0.70) |

The sweep's `n_species_detected` becomes `n_species_labels_qc_passed` (unique
labels among QC-passed records). Label classification lives in a new
`boldgenotyper/taxon_labels.py` (`label_level()`, `genus_of()`), shared with the
query tool (Q5) and label-conflict evidence (P1-7).

### P0-10 `processid`

The QC-passed FASTA header becomes the bare `processid`, so the haplotype
mapping and every CSV use one format. The `processid_base` string surgery in
`cli.py` goes away.

### P0-12 Single load and fresh log

`setup_logging` gains `mode` (default `'w'` for pipeline runs), and the first
lines of every log are a run header: BOLDGenotyper version, run start time,
command line, output directory. A test asserts that `run_pipeline` calls
`metadata.parse_bold_tsv` exactly once, and another that running
`setup_logging` twice on one path leaves one run header.

**Reused output folders.** Because a run overwrites files in place, files from
an earlier run (possibly a v1 run with a different layout) can sit next to the
new ones. At the start of `run_pipeline`, before anything is written, the output
folder is checked for markers of a previous run: `run_provenance.json`,
`*_pipeline_parameters.json` (v1), `*_annotated.csv`, `records.csv`,
`haplotypes.fasta`, or a `haplotypes/` folder. If any is present, the run
continues but records a `StepWarnings` entry ("Output folder already holds a
previous run (…); files from that run that this run does not overwrite remain
and may be stale"), so it appears in the log, in the end-of-run summary and in
provenance. The run's own log file is not a marker (it has just been created).

### Query tool (Phase 2)

Extends the 2026-07-28 verdict design (`query_assignment.assign_query`); the
pure-function seam stays.

- **Q1 Input.** Strip `-`, `.` and whitespace; uppercase. If any input
  sequence contained gap characters, log a warning that the input looks aligned.
  `query_length` is the ungapped length.
- **Q2 Indels.** From the overlap alignment (see Decisions; local alignment hid terminal mismatches): `n_mismatches`, `n_gaps` (gap
  columns inside the aligned block, both sides), and `indel_in_query` = any gap
  run whose length is not a multiple of 3. Identity keeps its current definition
  (matches / aligned positions without gaps) but is no longer the only number.
  Optional `--check-frame` is deferred unless time allows.
- **Q3 Coverage.** `query_coverage` = query bases inside the aligned block /
  `query_length` (reported). `--min-query-coverage` (default 0.95) applies to
  query bases inside the aligned block / min(`query_length`,
  `haplotype_length`), so a query longer than the reference core can still
  match it; lower-coverage matches are flagged `low_coverage` and excluded from
  the call. Ranking: (coverage, identity, aligned length), descending.
- **Q4 Ties and equivalence.** Differences `d = n_mismatches + n_gaps`. The
  equivalence set = eligible haplotypes with `d ≤ d_best + max_mismatch_delta`.
  A column `set_identical_over_region` states whether the members are identical
  to one another over the query's aligned region (true whenever the best match
  is exact and delta is 0): computed by comparing the haplotype substrings the
  query aligned to, so no MSA is needed. `n_equivalent` = set size.
- **Q5 Genus-only labels** are compatible with their congeners: they neither
  count against a species call nor break a single-species set.
- **Q6 Species support.** Pooled member labels across the equivalence set,
  including `assigned_corrected` members (stated in the output header):
  `pooled_member_labels` (e.g. `Genus alpha 42; Genus beta 4; Genus 3`),
  `species_call` and `species_support` = count of the leading species / count of
  species-level labels in the pool (genus-only congeners and missing labels
  excluded and reported separately). A `species_call` needs `species_support`
  of at least `--min-species-support` (default 0.70). Against a v1 run folder
  (no record statuses), species support is not computed: `species_call` is
  `unknown` with a message that it needs a v2 run folder.
- **Q7** `match_quality` and its help text are removed; numbers only.
- **Q8** `n_reference_haplotypes` is the number searched.
- **Q9** A `reference_run` block (md5 of `run_provenance.json`, version,
  `n_haplotypes`, run date) in the JSON, and as `#` comment lines above the CSV
  header, plus a `reference_run_id` column.
- **Q10** `--search-records` searches all QC-passed reference records
  (`records_qc_passed.fasta`, written by the pipeline from Phase 2 on) and
  reports exact-match records with their labels.
- `query_summary.csv` columns: as proposed in the review (`query_id,
  query_length, aligned_length, query_coverage, n_mismatches, n_gaps,
  best_identity, call_level, equivalence_set, n_equivalent,
  pooled_member_labels, species_call, species_support, flags,
  reference_run_id`), plus `set_identical_over_region`. `call_level` is
  `haplotype` (one haplotype), `haplotype_set` (several) or `none`.

### P1 Default interpretations (Phase 3)

`--extended` is introduced. Threshold interpretations are deleted or reworded
(P1-1). `potential_misidentifications.csv` → `label_conflicts.csv` with evidence
columns (`n_members`, `n_majority`, `majority_fraction`, distance to the nearest
haplotype of the record's labeled species) instead of "confidence" (P1-7);
"contamination" → "label conflict", with missing labels reported separately
(P1-6). Cross-tabs, temporal and "emergence" outputs, the barcoding gap (as
`label_based_gap`, computed on records, excluding label-conflict records) and
diversity metrics move behind `--extended` (P1-2–P1-5, P1-10). Metadata
vocabularies are normalized (P1-5). `representativeness` and the range bounding
boxes are removed (P1-9, P1-10). Depositor keyword hits keep the raw note and
show the matched pattern, called a keyword hit, not a category (P1-8).

### P2 Layout and P3 polish (Phase 4)

Default layout:

```
<Organism>_BOLDGenotyper/
├── README.md                 # auto-generated: every file and column, with definitions
├── run_provenance.json
├── <Organism>_pipeline.log   # ends with the WARNINGS summary
├── records.csv               # one row per unique input record
├── records_qc_passed.fasta   # for boldgenotyper-query --search-records
├── haplotypes.fasta
├── haplotypes.csv            # one row per haplotype (merges the four taxonomy tables)
├── label_conflicts.csv
├── divergence/   haplotypes_aligned.fasta, pairwise_p_distance.csv
├── phylogeny/    tree.nwk, excluded_tips.txt, tree.pdf/.svg
├── geography/    haplotype_by_region.csv, distribution_map.pdf/.svg   (only with coordinates)
└── report.html               # < 10 MB; links to files instead of embedding them
Optional: --extended → extended/;  --export-format → exports/;  --plot-kit → plots/
```

The confirmed duplicates are removed; `report.html` links rather than embeds;
the divergence README path error is fixed. P3: PNG size/dpi caps, one MSA
format by default, no mixed ✓/plain log lines, and the sweep's
`recommendations.txt` reports the elbow with a stability metric (share of
samples whose haplotype changes between adjacent thresholds, from
`group_membership_tracking.csv`) instead of an "acceptable range."

Flag changes that follow from the layout (all kept as deprecated aliases):
`--export-format` stops defaulting to `all` (exports only on request;
`--no-export-format` becomes a no-op); plot kits become opt-in via `--plot-kit`
(`--no-export-plot-data` becomes a no-op); metadata cross-tabs and temporal
analysis moved behind `--extended` in Phase 3 (`--no-metadata-summary` and
`--no-temporal-analysis` now only restrict what `--extended` adds; metadata
coverage is always written).

## Testing

- Every P0 and Q item gets a test. New tests use synthetic sequences or small
  public-data fixtures in `tests/data/` (already whitelisted in `.gitignore`).
- One small end-to-end test runs `run_pipeline` on a synthetic TSV in a
  temporary directory (skipped if MAFFT is absent) and checks statuses, IDs,
  provenance and the log.
- **Collectability.** A `tests/conftest.py` with `collect_ignore` lists the nine
  script-style files (no test functions; they exit, write logs, load map data
  or read local run outputs at import) and `test_genotype_assignment.py`, which
  imports a module removed before v1.0.0. No file is deleted. With that, a bare `pytest`
  runs, and Phase 7's `pytest --cov=boldgenotyper` can produce a coverage table.
- Pre-existing failures in files an item touches are repaired when the item
  changes the code they test (for example the coordinate tests in
  `test_error_handling.py` under P0-4); others are left and listed.

## Risks

- **Scope.** P1–P3 touch most modules. Each phase stops for review, and the
  migration table is built incrementally as files are renamed.
- **`'Unknown'` removal** reaches plotting and export code that filters on the
  string. Each module gets a test with a NaN region before its comparisons change.
- **Haplotype set drift.** Refactoring dereplication could change the set.
  Guarded by a synthetic test that asserts the retained sequences are identical
  before and after correction is enabled, and by the Phase 7 v1/v2 `seq_md5`
  comparison.
