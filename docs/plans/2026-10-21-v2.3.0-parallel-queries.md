# BOLDGenotyper 2.3.0: run queries in parallel

**Status (2026-10-21): done on `release/v2.3.0`, awaiting review before the tag.**

**Why.** `boldgenotyper-query` aligns each query to every haplotype in one process (Biopython
`PairwiseAligner` with traceback, ~4 ms per pair; a profile puts 96% of the time in the
aligner). Against a family-level reference of 1,910 haplotypes a query takes ~7.8 s. The tool
paper's query benchmark (7 datasets × 5 folds × 4 windows) and mislabel injection (45
reference runs) would have taken more than 200 hours.

**Change.** `--threads N` (`threads` in `query_against_haplotypes`, default 1): queries are
aligned in N worker processes (`concurrent.futures.ProcessPoolExecutor`). Each worker gets the
haplotypes once through the pool initializer and builds its own aligner; whole queries are
mapped in order, so ranking, calls, logging and outputs stay in the main process and come out
the same for any N. With 1 thread nothing changes: no pool, one aligner, as in 2.2.0. A
number below 1 is an error (`--threads 0` is a usage error). `query_provenance.json` records
`threads`.

**Not done.** A first pass by alignment score that fully aligns only the best few haplotypes
would be faster, but the ranking uses coverage, differences and identity, not the score, so
it could change calls.

**Calls made here (for Steph's review).** Default 1 (the 2.2.0 behavior); worker
processes rather than threads, so the alignments run in parallel whatever the aligner does
with Python's interpreter lock.

**Checks.**
- Tests: `tests/test_query_threads.py` (identical AlignmentResult and verdict lists for 1, 2
  and 32 workers; threads below 1 refused) and `tests/test_query_cli.py` (identical
  `query_calls.csv` and `query_candidates.csv`, `query_alignments.txt` identical apart from its
  date line, for `--threads 2`; `--threads 0` a usage error).
- 100 full-length Pieridae queries against its 2.2.0 full run (1,910 haplotypes): 776 s on
  2.2.0, 143 s with `--threads 8`, 113 s with `--threads 12` (Apple M4 Pro); `query_calls.csv`
  and `query_candidates.csv` byte-identical to 2.2.0's, `query_alignments.txt` identical
  apart from the date.
