Date: 2026-10-05
Status: approved 2026-10-05; plan: `2026-10-05-v2.0.0-evidence-taxa-plan.md`
Branch: `release/v2.0.0` (not pushed; these changes go into 2.0.0)
Follows: `2026-10-04-v2.0.0-outputs-design.md` (§2, haplotype taxa: evidence and curation)
Implementation: Phase 14; its plan is written after this addendum is approved

## Context

In 2.0.0 as built (Phases 8–13), a haplotype's taxon comes from its member labels: the
leading species when it holds more than 0.70 of the counted labels, otherwise the
members' most common genus. Evidence for the taxon (distance, BIN, tree) is reported in
`haplotypes.csv` with a `suggested_sp`, but never applied; a user who accepts a
suggestion writes a curation file and runs again.

On the 2.0.0 verification run (483 haplotypes), 54 haplotypes are left at genus:

- 31 have no species-level label (only open nomenclature such as "Genus sp. 1" or
  "Genus cf. alpha", or genus-only labels);
- 20 have two or more species labels, none above 0.70;
- 3 have one species label, outweighed by labels of another genus.

Fourteen carry a suggestion. Genus-level calls for haplotypes whose evidence clearly
names one species make results hard to read (maps, tree labels and queries say "Genus"),
and curating each one by hand is slow. Two findings from the review shape the fix:

1. **The tree line reads unsupported clades.** It takes the smallest clade holding the
   haplotype and another species-level haplotype, then abstains when that clade's
   support is below 0.70. In dense groups FastTree gives near-zero branches a support of
   0.00, so the line abstains even when the next clade up is well supported and holds
   only one taxon (one verification-run haplotype: two clades of support 0.00, then one
   of 0.85 holding five haplotypes of the same species).
2. **Some suggestions contradict the haplotype's own labels.** Evidence can only name
   species that other haplotypes carry at species level, so it favors described species.
   H0094 (12 of 17 members labeled as undescribed *Iago* species, 5 as *Mustelus mosis*)
   gets *M. mosis*; H0168 (labels lead with *Apristurus pinguis*, 5 of 9) gets
   *A. ampliceps*. Applying every suggestion would overrule label majorities.

## Decisions (Steph, 2026-10-05)

1. Apply evidence automatically when it picks the haplotype's own leading species label
   (option B of the review), on by default with an opt-out.
2. The tree line collapses branches with support below 0.70 before reading the sister
   clade.
3. The run writes a pre-filled curation file with the suggestions it did not apply.
4. Runs rely on the evidence rule where it applies; curation files are for calls the rule
   cannot make.

## Goals

- A genus-level haplotype whose evidence names its leading species label gets that
  species, marked as set by evidence, in every output that shows a taxon.
- The label rule's own result stays visible.
- Suggestions the rule does not apply are one edit away from a curation file.

## Non-goals

- Evidence never changes a species-level call of the label rule, and never assigns a
  species that no member's label names.
- No chaining: evidence for one haplotype never uses another haplotype's evidence taxon.
- The label rule and its 0.70 threshold are unchanged.
- No change to how evidence lines other than the tree line are computed.

## Design

### 1. The evidence rule

A haplotype takes its taxon from evidence when all of the following hold:

1. the label rule left it at genus (`assignment_level` = `genus`), and it is not curated;
2. it has a `suggested_sp`: at least two of the three lines (distance within the nearest
   species' spread; BIN majority at 0.70 or more; tree, §2) name that species, and none
   names another;
3. `suggested_sp` is the haplotype's leading species-level label, as the label rule
   computes it (`taxon_labels.pool_labels`; reported as `majority_label`; none when two
   species tie);
4. `suggested_sp` is in the genus the label rule assigned.

Effect: `assigned_sp` = `suggested_sp`, `assignment_level` = `species`,
`assignment_source` = `evidence`, and `assignment_notes` =
`evidence: <suggestion_basis>; labels: <the label rule's note>` (e.g. `evidence:
distance, tree agree; labels: majority 0.56 not above 0.70; fell back to genus`).
`majority_label`, `majority_fraction`, `suggested_sp` and `suggestion_basis` are
unchanged, so the label rule's result and the evidence stay visible.

**Precedence:** curated, then evidence, then labels. A curation row overrides an evidence
taxon, including back to a genus.

**One pass:** evidence is computed from the label rule's and curated taxa, then applied;
haplotypes set by evidence are not used as references for other haplotypes' evidence. The
result does not depend on the order of haplotypes.

**Without a tree** (no `--build-tree`), only distance and BIN can name a taxon, so both
must agree.

### 2. Tree line: collapse unsupported branches

`tree_sister_taxon` and `tree_sister_support` are read from the tree with every branch of
support below 0.70 (`TREE_MIN_SUPPORT`), or without a support value, collapsed:

- walking from the haplotype's tip toward the root, skip clades whose support is below
  0.70; the first remaining clade that holds at least one other species-level haplotype
  is the sister clade;
- `tree_sister_taxon` is the taxon those species-level haplotypes share (empty when they
  differ), and `tree_sister_support` is that clade's support (0.70 or more);
- the root never counts (it holds every taxon of the run).

The line then names a taxon only from a supported clade, so the "tree support below 0.70"
abstention disappears; `suggestion_basis` says "no supported clade names one taxon" when
the tree line is empty. On the verification run this changes one haplotype's tree line
(support 0.00 → 0.85) and no other suggestion.

### 3. Where it runs: the tree moves ahead of the taxon's users

Evidence needs the tree. Several outputs read the taxon before the tree is built today:
label conflicts (Phase 6), species aggregation (6.5), outgroup rooting by taxon and the
relabeled tree (8), divergence (9), figures (10), summary (12). Applying evidence at the
layout step (13), where it is computed now, would leave all of them on the label rule's
taxa.

The tree build and rooting (current step 8.1) does not depend on anything after Phase 5,
so it moves into Phase 5:

| Step | What |
|---|---|
| 5.1 | label rule (unchanged) |
| 5.2 | curation (unchanged); taxonomy table written (read by outgroup-taxon rooting) |
| 5.3 | tree: tip selection, MAFFT, FastTree, rooting (moved from 8.1; outgroup-taxon rooting uses the label rule's and curated taxa) |
| 5.4 | taxon evidence for every haplotype; evidence taxa applied (§1) |
| 5.5 | taxonomy table rewritten and merged into the records (as now) |

Phase 8 keeps relabeling and the alignment plots; Phase 13 writes the stored evidence to
`haplotypes.csv` instead of computing it. Evidence reads the records as `records.csv`
will show them (labels, BINs, institutions, QC flags); geography is not needed. Warning
step names follow the move (`5 tree`, `5 tree reroot`, `5 taxon evidence`).

Considered and rejected: computing evidence late and recomputing every taxon-dependent
output afterwards (Phases 6–12 twice, and two versions of the taxonomy table in one run).

### 4. Everything that reads a taxon

Evidence taxa are treated like curated taxa:

- **Label conflicts** compare each member's label with the evidence taxon
  (`taxon_curation.curated_taxa` becomes "taxa not from labels": curated or evidence).
  `label_conflicts.csv` already has `haplotype_taxon` and `assignment_source`.
- **Species aggregation** (6.5) counts a haplotype by `assignment_level` = `species`
  instead of `majority_fraction` ≥ 0.70. This also fixes curated taxa, which are left out
  today.
- **Tree labels, figures, divergence, summary counts** follow `assigned_sp` and need no
  change.
- **Queries** (`query_assignment.load_haplotype_taxa`): a set holding a haplotype whose
  taxon is curated or set by evidence is called from the haplotypes' taxa (`call_basis` =
  `haplotype taxa`). The flag `curated_taxa_disagree` is renamed `haplotype_taxa_disagree`
  (2.0.0 is not released): a haplotype with a curated or evidence taxon is in the set and
  the set's taxa differ, or one is not at species level. Query-time `--taxon-curation` overrides evidence taxa as it
  overrides the run's curated taxa.

### 5. Outputs

| Output | Change |
|---|---|
| `haplotypes.csv` | `assignment_source`: `labels`, `evidence` or `curated`; `tree_sister_*` defined as in §2 |
| `records.csv` | `assigned_sp`, `haplotype_label`, `assignment_*` follow the haplotype |
| `taxon_curation_suggestions.csv` (new, run root) | one row per suggestion not applied: `seq_md5`, `sequence` (core), `taxon` (= `suggested_sp`), `reason` (`suggested by evidence: <basis>; labels: <labels>`), `curator` and `date` empty, then `haplotype_id`, `assigned_sp`, `why_not_applied` for reading. Written only when there is a row. It loads as a curation file (extra columns are ignored), so a user deletes the rows they reject and passes it to `--taxon-curation` (pipeline or query) |
| `run_provenance.json` | `applied.taxon_evidence`: `apply` (bool), `tree` (bool), `n_applied`, `n_suggested_not_applied`, `suggestions_file` |
| `README.md` (run) | the rule, the three sources, the suggestions file, the new tree-line definition |
| `report.html` | Taxonomy: a "Taxa set by evidence" table (taxon, labels, `majority_fraction`, `suggestion_basis`) beside curated taxa; "Needs attention" lists the remaining suggestions and points to the suggestions file; Overview: a key finding with the count; Methods: the rule (below) |
| `summary.csv` | no new columns; species-level counts include evidence taxa |

`why_not_applied` values: `not the leading label`, `leading label tied`, `another genus
than the label rule's`, `no species-level label`, `evidence taxa off`
(`--no-evidence-taxa`).

Methods sentence (report, run README):

> Haplotypes left at genus by the label rule took the species of their leading label when
> at least two of three lines of evidence named that species and none named another: the
> nearest species-level haplotype lay within that species' observed spread; the majority
> label of the members' BOLD BIN reached 0.70; the smallest clade with SH-like support of
> 0.70 or more holding other species-level haplotypes held only that species. *N*
> haplotypes were assigned this way.

When the rule is off: "Evidence was reported but not applied (`--no-evidence-taxa`)."

### 6. Opt-out

`boldgenotyper --no-evidence-taxa` (config `taxonomy.apply_evidence`, default `true`):
evidence is computed and reported, suggestions are written to the suggestions file, and no
taxon is changed. `boldgenotyper-query` uses the reference run's taxa as recorded; it has
no flag of its own.

### 7. Expected effect on the verification run

From the verification run's outputs (scratch computation, not a run):

- 9 haplotypes set by evidence (among them *Loxodon macrorhinus*, whose members carry 2
  species labels, 13 "cf." labels of that species and 1 label of another genus; and
  *Carcharhinus tjutjot*, 7 of 10 labels, exactly at 0.70);
- 6 suggestions written to the suggestions file (H0094 and H0168 above; three haplotypes
  with no species-level label; one with tied labels);
- 39 haplotypes stay at genus without a suggestion.

`records.csv` and `haplotypes.csv` change only for the 9 haplotypes and their members;
`label_conflicts.csv` changes for those haplotypes; the tree is unchanged (same input, now
built in Phase 5).

## Testing

- Tree line: a synthetic Newick in which the nearest clades have support 0.00 and the
  first supported clade holds one taxon (named), two taxa (empty), or only the root
  (empty); clades without a support value are collapsed.
- Rule: one test per condition of §1 (each failing condition leaves the label rule's
  taxon, with its `why_not_applied`); curated over evidence; no chaining (a haplotype
  whose only species-level neighbor is itself set by evidence gets no tree or distance
  line from it); without a tree.
- Suggestions file: written only with rows; `load_curation` reads it; passing it back with
  `--taxon-curation` applies its rows.
- Pipeline (synthetic dataset): a genus-level haplotype set by evidence shows `evidence`
  in `haplotypes.csv` and `records.csv`, its members' label conflicts are judged against
  it, and the relabeled tree and figures use it; `--no-evidence-taxa` leaves it at genus;
  the tree is the same as before the move.
- Query: `call_basis` = `haplotype taxa` for a set with an evidence taxon; the renamed
  flag.
- Report and README: the table, the finding, the methods sentence, every new file and
  column documented.
- Verification: the verification input again, compared with the Phase 13 run (differences
  confined as in §7), and a scratch check of the shared reference run's dataset.

## Risks

- **A wrong evidence call.** Mitigated by requiring two agreeing lines, none against, and
  agreement with the members' own leading label in the same genus; every evidence taxon is
  marked, listed in the report, and reversible with a curation row or the opt-out.
- **Changed counts.** Species-level counts and label conflicts change between runs with
  and without the rule; provenance records whether it was applied.
- **Pipeline order.** Building the tree earlier changes the log's phase layout; the tree
  itself is unchanged (verified by comparing splits and supports).
